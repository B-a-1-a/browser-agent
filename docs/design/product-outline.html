Customer pain points

Consolidated from your customer-needs research and notes:

Repetitive work and lost learning

  • Tedious, repetitive browser work.
  • Copying information between disconnected web apps.
  • Re-entering information from local files into online forms.
  • Manually checking websites for changes.
  • Repeated alerts without meaningful changes.
  • Repeating instructions for recurring tasks.
  • Relearning workarounds that previously succeeded.

Setup, access, and dependence on tools

  • Unclear use cases and confusing starting experiences.
  • Complicated setup and workflow builders.
  • Forced browser switching and disrupted browsing habits.
  • Losing workflows when vendors change or discontinue products.
  • Limited accessibility, platform support, and regional availability.

Barriers that stop agents

  • Login, two-factor authentication, CAPTCHA, and bot-protection barriers.
  • Account restrictions caused by automation.

Reliability and task context

  • Broken connections and frequent disconnections.
  • Lost sessions, task history, and unfinished work.
  • Having to restart work that cannot be resumed.
  • Tasks using the wrong tabs, accounts, or context.

Oversight and control

  • Agents interrupting normal browser use.
  • Having to watch and repeatedly check agents.
  • Excessive, difficult-to-understand approval prompts.
  • Unwanted submissions, messages, purchases, or deletions.

Trust and usable results

  • Incorrect or incomplete work reported as successful.
  • Little visibility into agent activity.
  • Missing proof of completion.
  • Difficulty turning research into usable files, tables, or digests.

Speed, costs, and usage limits

  • Slow task execution.
  • Unpredictable costs and surprise bills.
  • Paying for failed or incorrect runs.
  • Paying again despite an existing AI subscription.
  • Usage limits interrupting tasks.
  • Changing credits, pricing, and plan entitlements.

Privacy and security

  • Exposure of sensitive information.
  • Unsafe behavior caused by malicious webpage instructions.

Additional pain hypotheses from your notes

  • Fragmented management across AI providers.
  • Difficulty maintaining reusable, purpose-specific task profiles.
  • Unnecessary refusals interrupting legitimate work.

Feature list, in the order users encounter it

  1. First launch: connect existing tools
    • Connect supported agents using existing subscriptions.
    • Create a built-in browser profile and sign into websites inside the app.
    • Grant optional folder access.
    • Check connection health; reconnect when needed.
  2. Home: organize work
    • Create workspaces/projects.
    • View tasks, recent results, and running work.
    • Open a shared Needs you inbox.
    • Start from templates for admin, personal productivity, and study.
  3. Workspace setup: establish reusable context
    • Save task profiles containing instructions, preferences, and reference files.
    • Select persistent built-in browser profiles containing signed-in accounts.
    • Set default permissions for websites, files, and actions.
    • Keep task conversations and context separate.
  4. New task: describe the desired outcome
    • Enter a request or choose a saved task profile.
    • Attach files, pages, and relevant context.
    • Choose the lead agent, model, and available execution options.
    • Choose Ask, Auto within rules, or Custom permissions.
    • Choose where generated files should be saved.
  5. Plan review: agree on execution
    • Automatically propose steps and browser workers.
    • Edit the plan; add, remove, or override workers.
    • Set concurrency, usage budgets, and stopping conditions.
    • Show provider-reported usage and clearly labeled estimates where available.
    • Enforce permissions in the app, independently of model instructions.
  6. Task workspace: coordinate the work
    • One shared task conversation.
    • A grid of browser workers with previews, activity, and status.
    • Expand a worker to inspect its built-in browser tab, instructions, and activity.
    • Add workers or change their assigned agent/model.
    • Read, create, edit, and save local files.
    • Run tasks in the background; coordinate conflicting account actions.
    • Pause, resume, stop a task, or stop all work.
    • Retry/reconnect failed workers; queue work when usage limits are reached.
  7. Intervention: act when needed
    • Review the exact destination, content, attachments, and proposed action.
    • Approve individually or in a clearly scoped batch.
    • Override workspace permissions for a particular task.
    • Take over the built-in browser for login, CAPTCHA, or other blockers, then resume.
    • Notify users about meaningful changes, completion, failures, and required action.
  8. Results: verify the outcome
    • Separate Results view.
    • Completed, blocked, skipped, and failed items.
    • Confirmation evidence, screenshots, source links, and submitted fields.
    • Deliverables, action history, checkpoints, and recovery options.
    • Duration and usage information where measurable.
  9. Reuse: turn successful work into a routine
    • Save a completed task as a reusable workflow.
    • Run it again with new inputs.
    • Schedule recurring work and meaningful-change alerts.
    • Export/import portable instructions and workflow definitions.

For a local desktop version, scheduled work requires the app to be running and the computer awake.

I’d keep teaching by demonstration, automatic model routing, VPN/proxy settings, and automatic CAPTCHA handling as later explorations. The initial blocker flow should support human takeover.

Typical user journey: job applications

  1. Connect an existing agent subscription, create a built-in browser profile, and sign into job websites inside the app.
  2. Create Job Applications, add a resume, and save role preferences.
  3. Request: “Find today’s matching jobs and prepare applications.”
  4. Review the proposed plan and workers; keep submission approval enabled.
  5. Workers find roles, compare requirements, and prepare applications in parallel.
  6. Take over a blocked portal inside the app to sign in, then return control.
  7. Review prepared applications and approve selected submissions.
  8. Inspect confirmations and unfinished items in Results.
  9. Save the task as a weekday routine.

Browser recommendation

Here, “built-in browser” means an app-managed browser used for agent work; it would not have to replace the user’s everyday browser.

ApproachProsCons
App-managed built-in browserConsistent in-app control; easier management of separate browser profiles; more control over browser lifecycle.Additional sign-ins and migration friction; larger maintenance burden; responsibility for shipping browser security updates.
Connect to the existing browserReuses signed-in sessions; familiar accounts and extensions; less migration; browser vendor handles browser updates.Connection and permission setup; shared account state; interference from user changes; interruptions if the browser closes.

Let’s use T3’s built-in browser. Users create browser profiles and sign into websites inside the app. Workers use tabs belonging to those profiles. Clicking a tile opens its browser; takeover happens inside the app.

Supported cookie import can reduce setup, although some websites require another sign-in. Workers sharing a profile also share account state.

Technical implementation plan

  • Starting point: The source snapshot from T3 Code release v0.1.2, manually copied into our repository with attribution and upstream licensing preserved.
  • Desktop and browser: Electron, React, and TypeScript. Reuse T3’s built-in browser, persistent signed-in profiles, browser control, and human takeover. Keep its existing Playwright/CDP connection initially.
  • Agent runtime: Codex first through its supported subscription connection. Reuse T3’s provider adapters, persistent sessions, orchestration, delegation, and local file tools. Add reusable task profiles, a shared task conversation, browser-worker tiles, app-enforced permissions, and verified results.
  • Stagehand: Evaluate Stagehand v4 behind a replaceable browser-control interface. Its extension runtime is not a direct replacement for T3’s Electron browser connection. Measure compatibility, speed, and usage on our workflows before adoption.
  • Step one — Bala: Validate and stabilize the inherited core, configure app identity and updates, establish permissions, and verify build and test tooling before contributors begin separate implementation issues.
